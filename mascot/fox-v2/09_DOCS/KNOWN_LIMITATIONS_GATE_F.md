# Known limitations — Gate F

| # | Limitation | Impact | Planned / mitigation |
|---|---|---|---|
| 1 | **Mobile performance is unverified.** There was no real phone or tablet available. Only an emulated 390 × 844 viewport with touch input was tested (layout + tap → head_pet), in headless Chrome without a GPU. | No FPS, thermal or memory data on mobile GPUs. | Test on a real mid-range Android and an iPhone before LifeQuest Web ships the companion on mobile. Consider DPR 1 and the mini presentation only on phones. |
| 2 | **Several LifeQuest events have no matching clip** in the E2 contract (HABIT_CHECKED_IN, STREAK_LOST, CHALLENGE_LOST, QUEST_DEADLINE_URGENT, QUEST_EXPIRED, USER_IDLE). | They use documented face-only or activity fallbacks; the body keeps idling. Nothing is fabricated. | Gate G clips (`plannedClip` in the registry: proud_pose, sad_react, panic, disappointed, sleep_loop, celebrate, level_up, streak_cheer). |
| 3 | **`resting` is a fallback activity** (idle clip at 0.8× + sleepy face). | Reads as "drowsy", not asleep. | Gate G `sleep_loop`. |
| 4 | **One WebGL context per canvas.** Geometry is shared on the CPU, but each canvas uploads its own GPU buffers. | Mini + widget together = 2 contexts and ≈ 2 × 73.8k triangles. | Production: one live 3D companion per screen (integration guide §2). A single-renderer / scissor approach is possible later if needed. |
| 5 | **The GLB is not geometry-compressed** (2.7 MB, no Draco / meshopt). | ≈ 2.7 MB first download. Parse is fast (≈ 26 ms on the test laptop). | Meshopt is an export option for a later gate. Transfer compression already helps. |
| 6 | **Headless Chrome tab switching** keeps tabs "visible", so the automated tab pause / resume check simulates `visibilitychange`. | The real browser event path is verified only in the GPU session (see the runtime report). | – |
| 7 | **Heap after mount / unmount** still grows by ≈ 17 KB per cycle after warm-up (headless measurement; the leak of ≈ 400 KB per cycle was found and fixed in this gate). | Negligible for normal navigation. | Re-check in a long-session soak test in the real app. |
| 8 | **A queued event reaction can expire** (TTL 8 s) if higher-priority clips keep playing. Its deferred mood is then dropped as well. | A very busy burst of events loses its least important reactions, by design. | Tune TTL or queue size per product needs. |
| 9 | **Orbit (full view)** allows free rotation within limits. Look-at math follows the camera, but extreme top-down angles were not polished. | Only in the full view. | Clamp further, or remove orbit in production if not wanted. |
| 10 | **The dashboard is a mock.** Texts, data and the user name "Huy" (taken from the Dashboard UI V1 prototype) are sample data. | Visual QA only. | Full LifeQuest frontend is out of scope for Gate F. |
| 11 | **Two companions at once were not verified at 60 Hz on the GPU.** During the dashboard runs the host app throttled the browser pane (page rAF 15–30 Hz) because its window was not in the foreground. In all stable runs each companion rendered every page frame (≈ 0.3–0.6 ms update + 1.2–2.0 ms render submit per companion). One early run at 60 Hz page rAF showed 31 / 16 fps and could not be reproduced. | No performance approval for the 2-canvas layout. A single companion was verified at 59.7 fps. | Use one live companion per screen. Re-measure the dashboard on a foreground browser window. |
| 12 | **Re-mounting a companion takes ≈ 0.9 s on the test laptop** (new WebGL context + shader compilation on ANGLE / D3D11; the GLB itself comes from the cache). | A visible gap when the companion is toggled off and on. | To hide temporarily, keep the canvas mounted and pass `suspended` (the render loop stops, nothing is destroyed); unmount only when leaving the page or when the user disables the mascot. |
| 13 | **Simultaneous one-shots are not mixed.** Exactly one clip owns the one-shot layer, plus at most one fading out. | Intentional: avoids pose soup. | – |
